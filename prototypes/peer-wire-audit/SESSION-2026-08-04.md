## ⛔ Precondition 2 cannot be met today — #620 blocks it

**TypeScript has not been touched, and must not be.**

Precondition 2 requires a paid write to increment `CLAIMS()` on *both* boxes.
Reaching it means routing the store prefixes across the peering. **That would
create a free-write path on `g.toon`**, which is strictly worse than today:

- `app_route_price` answers **`no locally-terminated route matches`** for a
  `peer_id` route — confirmed live on the apex box, not merely inferred.
- A `peer_id` route carrying a `price` is a **hard config error**
  (`route.rs`: "`price` is only meaningful alongside `handler_url`"), so there is
  no configuration that charges a client for a peer-forwarded route.
- So repointing `g.toon.store` would stop the apex charging clients 1000 *and*
  start it paying the store box from its own channel. Today's behaviour is "apex
  charges and keeps"; that change makes it "nobody charges and the apex pays".

**This is issue #620, still OPEN**, and #678's own issue body lists it under
"Blocked by". #678's gate (c) names it exactly: *"a peer-forwarded route that is
not charged is a free-write path on g.toon, and claims spent for free cannot be
recharged."*

The peering is therefore configured on both boxes and proven to authenticate, but
**no route names the peer** — deliberately, and recorded in both config files.
The routes move when #620 lands.

### #620 has since landed — ADR 0028

**PR #751 merged, #620 CLOSED.** A `[[routes]]` entry naming a `peer_id` now carries
**both** numbers: `price` (what this connector's client edge charges a client) and
`fee` (unchanged from ADR 0010 — what this hop retains). `price` is **required** on a
forwarded route (`PeerRouteMissingPrice` replaces `PeerRouteHasPrice`), so a forwarded
route can never be *silently* free — which is how issue #557's guard now covers the
peer-routed case.

The no-divergence property is structural rather than asserted: configured-route
selection now lives in one place, so the greeting, `ClientClaimGate`, watermark journal
and `GET /ilp/routes/price` cannot drift from what the router will actually do.

**Two hardenings that were not asked for and are worth keeping:**

1. **A priced forwarded route never carries more than it was paid.** `amount > price`
   → `F03`, refused before the claim is ingested. Without it a client paying `price`
   could have bought a forward of an arbitrary `amount - fee`, and the peer claim this
   node then signs would be real money it never collected — a drain vector, in the
   exact path being made deployable. Gated on `price > 0` so a deliberate free-carriage
   route keeps its behaviour.
2. **`handle_probe` short-circuits at a priced forwarded route**, closing the same
   vector via `/ilp/probe`.

Verified independently, not taken from the agent's report: six hermetic tests in
`connector-client-edge` pass, including
`a_forwarded_route_never_carries_more_value_than_its_price` and
`a_claim_below_the_price_never_crosses_the_peering`. The devnet config changes in that
PR are comment-only — the `price = 1` decision is intact.

**#620's second gap was split out as #752 rather than silently closed with it:** a
terminating connector still does not charge its route's `price` for a peer-wire
arrival. It does **not** block the cutover — the first hop's `price` covers the whole
path and the far end is paid through the peer claim exchange — but the far end cannot
yet *verify* it was paid enough.

### Devnet arithmetic for the store leg

ADR 0028's intended arithmetic is `amount == price`: the hop collects `price`, forwards
`price - fee`, earns `fee`. So the apex should price `g.toon.store` at **1002** with
**`fee = 2`**, delivering exactly the store's own committed `price = 1000`.

Pricing it at 1000 with a fee of 2 would deliver 998 — below the store's own price. That
works today only *because* #752 is open (the far end does not check), and would break
the moment #752 lands. 1002/2 is correct now and stays correct then. It raises the
client's cost for that prefix from 1000 to 1002.

## The apex is blocked on a discovery problem with no clean answer yet

The store box's announce is published in **`remote-paid`** mode: its TS connector sends a
paid packet to `g.toon.relay` through the apex every 300s. That dial targets the apex's
`location /`, so **moving the apex's default edge to Rust kills the store's announce.**

The announcer sidecar cannot replace it. `packages/announcer/src/publisher.ts` says so
outright — it publishes either over plain NIP-01 WS (useful "only against relays that
accept free WS writes") or to the relay's **private** `POST /write` ingress, and:

> per the issue's re-scope, v1 only needs the LOCAL-relay case, which was always free. If a
> future revision needs to reach a remote relay…

The store box has no local relay, and the apex's `/write` is private (exposing it publicly
would be a free-write path). So a store-box announcer would have nothing to publish
through.

Three options, none free:
1. **Extend the announcer to publish remote-paid** — the feature its own comment anticipates.
2. **Let the apex's announcer carry the store's routes.** It already advertises
   `routes.store = "g.toon.store"`, which now resolves across the peering and pays the store
   box. The store's own announce (`g.toon.ario` + its own endpoints, a different pubkey)
   would disappear from discovery.
3. **Accept a discovery gap** for the store box.

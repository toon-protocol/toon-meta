# Architectural Decisions

Curated, durable **cross-repo** decisions. ADR-lite: each is *decision → why*.

**toon-meta does not restate protocol law.** The connector owns it, in [`docs/adr/`](https://github.com/toon-protocol/connector/blob/main/docs/adr/README.md) (69 status-tracked records) and [`CONTEXT.md`](https://github.com/toon-protocol/connector/blob/main/CONTEXT.md). Below: the load-bearing records by number, then the decisions that are genuinely this repo's.

## Cross-repo decisions

- **The connector is a paid reverse proxy, and there are two roles.** It terminates payments the way nginx terminates SSL; **connector** and **app**, no third. *Why:* an app that must import a payment library is a worse product than one that is handed ordinary, already-paid HTTP. Consequence for every other repo: no repo re-verifies a claim, and no repo calls its service a BLS, an agent runtime or a backend.
- **Messages and money are one packet.** Every monetized flow is one PREPARE carrying both the payload and its covering claim (connector ADR 0042). *Why:* the core thesis; no invoice/settle round-trip, and nothing owed between packets for a counterparty to walk away inside.
- **USDC is the sole user-facing token**, on two chains — Base Sepolia (`evm:84532`) and Solana devnet. *Why:* simplicity; operator tokens stay invisible to users. Mina left the connector repository (ADR 0065-mina) — but a claim declaring `blockchain: "mina"` is still **refused by name**, wire behaviour owed to toon-client and not to be cleaned up.
- **TOON's value layer is the signed payment-channel claim — not SPSP, STREAM or payment-pointers.** SPSP kinds (23194/23195) were removed. Multi-hop atomicity is packet-level condition/fulfilment; there is no on-chain HTLC escrow. *Why:* a write is one packet and one claim; there is no stream to chunk and no quoting.
- **Prepaid, supply-driven pricing.** Providers advertise price in a replaceable Nostr event (`SkillDescriptor`, kind:10035); the request packet's amount IS the payment. *Why:* removes request-for-quote latency. The connector's own prices are published on its self-description, not announced.

## Boundaries

- **Claim validation lives ONLY in the connector.** An app receives ordinary HTTP that was already paid for, plus `X-TOON-Payer`/`X-TOON-Amount`/`X-TOON-Chain` when the delivering connector was the one paid (connector ADR 0040). *Why:* the connector is the only party holding channel state; re-validating downstream is double work and incorrect. The old seam — `localDelivery`, `POST /handle-packet`, `PaymentRequest`, `ConnectorNode`, `ClaimReceiver`, `SettlementMonitor` — is **deleted**, not moved.
- **There is no apex.** Every hop is a peering an operator wrote down; every PREPARE carries its covering claim and pays that peering's flat fee. *Why:* free-forwarding needed an apex to trust, a parent tag on every child, and an accumulation to settle in aggregate; all three were removed. The apex box was destroyed 2026-08-14.
- **An ILP address is self-asserted — a claim, not a grant.** Nothing allocates one; reachability is the only registry. *Why:* an address that needed granting would need a granter. Nothing answers at `g.toon`.
- **Trust degrades; money doesn't.** (TEE) Attestation state changes never trigger payment-channel closure. *Why:* trust is a gradient, not a gate.

## Repo split

- **Polyrepo with npm coupling for libraries and an image pin for deployment** (not a monorepo, not submodules). *Why:* per-team ownership; teams build/test/release without rebuilding the world.
- **`toon` (core+sdk) is libraries only.** *Why:* the library layer must build and publish independently of the payment engine — which is now a Rust binary it could not import anyway.
- **The connector publishes no npm package.** One static Rust binary, one OCI image, `ghcr.io/toon-protocol/connector:rust-main` plus dated release handles. `@toon-protocol/connector`, `@toon-protocol/shared` and `@toon-protocol/mina-zkapp` are gone. *Why:* there is no TypeScript connector left to depend on (ADR 0017 called it a prototype, and it was switched off).
- **A node repository pins the connector, not the reverse** (connector ADR 0068). relay, store and gas-station each pin a release handle in exactly one guarded place in their own `deploy/`. *Why:* both halves of an image/config pair belong in one repo; the connector repo holding a write credential into two other repos' deploy state is a wider blast radius than the bug it would fix.
- **Publish via `pnpm publish` / changesets, never `npm publish`.** *Why:* `npm publish` shipped unresolved `workspace:*`, making `sdk@0.5.0`/`town@0.4.0` uninstallable.
- **`g.toon.<name>` is how this fleet names itself, and that is a convention, not law.** The live nodes claim `g.toon.relay` and `g.toon.store`. *Why:* keeping names beneath one label keeps peers' routing tables small — a courtesy, never a delegation, and never an apex.

## Knowledge architecture

- **toon-meta is the shared context + skills hub**, distributed as a Claude Code plugin; each repo's `CLAUDE.md` links here. BMAD framework skills and the raw planning dump were removed in favor of this curated `context/`. *Why:* repos need accurate, low-noise shared context, not a 3000-line planning archive.

## Software factory (Forge)

- **Forge is a factory *consumer*, not just the factory *producer*.** Forge (`toon-protocol/Forge`, the factory manager from [#198](https://github.com/toon-protocol/toon-meta/issues/198)) runs its own `.sandcastle/` factory like every other execution repo — it is not exempt because it builds factories. *Why:* org doctrine is that every execution repo runs the two-zone pipeline; a factory manager that isn't itself manufactured has no dogfood.
- **Forge bootstraps hand-rolled, then self-stamps (the self-hosting-compiler order).** Forge's *first* `.sandcastle/` is hand-applied from the relay-extracted recipe (a stage-0 gate, exactly like the #178 repos); `forge-core`/`forge-cli` are then developed *under* that gate; once the CLI works, `forge new` regenerates Forge's own `.sandcastle/`. *Why:* it is the only bootstrap order that never runs **ungated codegen to produce the gate that gates it**; and it makes Forge's hand-rolled factory an instance of the very templates Forge stamps, so hand-rolling Forge = authoring those templates. *Rejected:* self-stamp-from-source-day-one (backwards — ungated codegen); gate-only-until-self-host (leaves Forge un-factoried during the whole build).
- **Two distinct self-hosting proofs, self-host first — they are non-redundant.** (1) *Self-host:* `forge new` regenerates Forge's own `.sandcastle/` and reaches **green parity** with the hand-rolled bootstrap — proves the CLI runs end-to-end and the templates are complete. (2) *External re-stamp:* `forge new` re-stamps an existing #178 repo (relay) to green parity with **its** hand-rolled `.sandcastle/` — proves Forge generalizes to a factory it did not author. *Why keep both:* self-host is incestuous (same authors wrote Forge's hand-rolled factory and the templates), so it cannot catch generalization bugs; the external re-stamp is the load-bearing surprise. Making self-host *replace* the external re-stamp would let Forge pass acceptance having only ever stamped itself — the exact case where "works on the repo it was tuned against" hides the bug.
- **Forge self-stamps with `forge new --blank` + the `node-pnpm` environment — it mints no archetype.** *Why:* an archetype is *named for the domain you build* and *only exists after a pilot proves it*; Forge builds tooling, not a domain, and there is exactly one Forge, so it can't earn an archetype (a `forge`/`factory` archetype would be a category error). *Deferred to the archetype-catalog issue (not #198):* the org's repos cluster into three shapes needing distinct oracles, so the non-`game` catalog is **`service`** (relay-shaped payment-fronted node service — env + deploy bundle + e2e/journey/deploy/image-publish oracle; pilot: relay) and **`spa`** (rig-web-shaped browser read surface — browser build + Pages deploy + Playwright/visual gate; pilot: rig-web). **Pure libraries** (`toon` core+sdk) and **one-offs** (Forge) stay `forge new --blank` + node-pnpm — *no* archetype, because a `node-lib` archetype would be barely more than the bare environment (no shared doctrine/oracle beyond the toolchain to justify minting one). Each archetype still obeys the mint-after-pilot law (≥1 merged `agent:implement` PR minted it) and "alternate opinions are new archetypes, not flags."
- **Forge has a *double* oracle-protected zone — its product IS oracle machinery.** Unlike other repos (one protected zone = their own `verify/`), the `templates/**` gate runners + archetype oracle skeletons Forge ships **are oracle code for downstream repos**. So two zones are protected under Rule 4 (diff-path check + CODEOWNERS): (i) Forge's own `verify/` + gate scripts, and (ii) the shipped `templates/**` gate runners. No PR touches a template gate-runner and the `forge-core` code that emits it in the same diff. *Why:* otherwise an agent PR could "green" a broken stamper by rewriting the very machinery that judges it.
- **Golden-stamp fixtures are the Forge oracle, and their regeneration is dispatch-gated.** Forge's signature gate tier (T2) diffs `forge new` output against **committed golden fixtures** of the stamped `.sandcastle/`/workflows/Dockerfile/`factory.toml`. Regenerating those fixtures runs **only** through `golden-regen.yml` behind the `oracle-owners` environment (Rule 5). *Why:* if one PR could edit both a template and the golden fixture that pins its expected output, the golden test would self-certify — the agent regenerates the expectation to match whatever it changed, and the check becomes theater.
- **Forge's steady-state factory runs `forge-core`; raw `@ai-hero/sandcastle` is only the throwaway stage-0 scaffold.** The hand-rolled bootstrap runs raw sandcastle `main.ts` (forge-core doesn't exist yet, identical to the 8 repos); the self-stamp **swaps the engine** to `forge-core` + `factory.toml`, and that forge-core-driven factory is what Forge runs from then on. *Why:* a factory manager whose own factory doesn't run its own engine isn't eating its dogfood, and it would leave forge-core's orchestration path with no repo exercising it in anger.
- **"Green parity" is behavioral, never byte-identical.** Because raw-sandcastle `.sandcastle/` and forge-core `.sandcastle/` are structurally different by construction, both self-host and external-re-stamp parity mean *"the gate goes green and a real `agent:implement` PR merges end-to-end under the forge-core-driven factory"* — **not** a file diff against the hand-rolled scaffold. *Why:* the self-stamp swaps the engine shape, so a textual diff would always fail and measures the wrong thing.
- **Forge is the 9th registry row, hand-added at bootstrap — not withheld for self-registration.** Forge joins the going-forward set (8→9) with its `FACTORY.md` row added by hand when its hand-rolled factory is scaffolded, and is marked the only `forge-core`-driven row. The self-stamp's `forge new` registration PR is then an **idempotent re-registration** (already-registered → parity/no-op). *Why:* withholding the row until self-registration would leave a *genuinely live* factory absent from the org's source of truth — "unregistered = doesn't exist" is a validation rule, not reality, and a running-but-unregistered Forge makes `FACTORY.md` lie by omission. The "both directions" guard (unregistered → doesn't exist; pin mismatch → fails) is proved with throwaway fixture registries + the external re-stamp, so registry accuracy needn't be sacrificed to test it.
- **Self-host parity is a nightly/dispatch tier, not a per-PR gate.** T4 (a forge-core-driven self-stamp reaching green/behavioral parity; `forge doctor` green on HEAD) runs nightly + on dispatch. *Why:* a full self-stamp is expensive and cross-referential; gating every PR on it would make Forge un-iterable, and regressions are better surfaced as triaged nightly issues than as a per-PR wall.
- **Forge inherits the factory runtime policy ([#202](https://github.com/toon-protocol/toon-meta/issues/202)), and its templates become that policy's canonical home.** #202 makes per-role model tiering (as decided then: planner = `claude-opus-4-8`; implementer + reviewer = `claude-sonnet-5` — **superseded 2026-08-05**: planner/merger/reviewer = `claude-opus-5`, implementer = `claude-sonnet-5`; FACTORY.md → Model tiering is the current value and templates must not bake in the old pins) and the context-budget ceiling (small slices + pre-dispatch splitting + stop-and-handoff prompts) org-wide. *(#202 originally stated that ceiling as "~60% of the context window"; it is now stated in absolute tokens — a ~200k cap, handoff by ~160k — so it means the same thing on every model. FACTORY.md → Context budget is the current value; templates must not bake in the old percentage.)* Two consequences for Forge: (i) **`FACTORY_SPEC.md` must express per-role models** — forge-core wraps sandcastle (whose four roles all default to Opus), so `factory.toml` needs a per-role model field (in `[loop]` or a `[models]` block) for forge-core to configure them; this is a spec requirement the epic's original `[loop]`/`[[oracle.tier]]` sketch omitted. (ii) **Forge's protected `templates/**` ship #202's tiering + context-budget handoff prompt as baked-in defaults**, so the policy propagates by `forge upgrade` (one template change + N gated PRs) instead of an 8-repo hand sweep — #202 is the poster-child example of why Forge exists. *Sequencing:* #202's policy must land in the hand-rolled 8 (the relay-proven pattern) **before** forge-core extracts templates, else Forge extracts a pre-#202 pattern and needs an immediate `forge upgrade`; so #202 is a dependency-edge *into* forge-core extraction, not a parallel afterthought. Forge's own two stories adopt the tiering at creation (stage-0 sets impl+review = Sonnet-5 by hand; self-host inherits it via forge-core).
- **Forge's factory ships as two stories at opposite ends of the epic, not one.** *Early* — `forge:bootstrap`: hand-rolled stage-0 `.sandcastle/` (raw sandcastle, relay recipe) + hand-added `FACTORY.md` row; depends only on the repo scaffold + relay recipe (**not** `FACTORY_SPEC.md`), and **blocks** forge-core (forge-core is developed under it). *Late* — `forge:self-host`: swap the engine to forge-core-driven `factory.toml`, reach green parity (the self-host checkpoint), wire T2 golden-stamp + T4 nightly self-parity + the double protected zone; **blocked by** forge-cli + templates, sequenced alongside/just after the external relay re-stamp, before the archetype catalog. *Why:* keeps "Forge is itself a factory" true from the earliest possible moment (a plain gate, day one) while deferring the expensive forge-core dogfood to when the CLI can deliver it — so Forge is never building factories while lacking one, and its longest/riskiest build window (forge-core + CLI) is gated.
